## 1. 两处口径修正

1. **“40 秒初扫”和“96.5 秒 extract”不是同一个阶段。** 40 秒是擦完后的第一轮残留复查（RUNBOOK:168），96.5 秒是擦除前的 OCR 建轨（版面约 10s + analyze 约 81s）。两个数都真，上一版汇报把“初扫”用混了，应分开写。
2. **两段式 OCR 的收益没有两倍。** 成片字幕覆盖率：103s 这条 52.9/103.4s（51%），另一条 111/157s（71%）。窗内仍要扫一半以上帧，粗扫再加一遍，理论只省 5–25%。要拿到 40% 以上必须先做“字幕带静止帧复用”，再加粗到细。

### P1 翻译质量（实验完成，待落地）

**实验（2026-11-03，fc66 的 38 条人工参考；exact / sim）**

| 方案 | 7B | 30B-A3B | 结论 |
|---|---:|---:|---|
| 生产 prompt 逐句 | **0.789 / 0.935**，2.3s | 0.184 / 0.682，19.2s（`--cpu-moe`） | 7B 综合最稳 |
| 术语表/上下文/风格指令 | 0.13–0.68 / 0.63–0.92 | 0.08–0.21 / 0.55–0.73 | 都会把好句改坏，不能进生产 |
| 官方默认 prompt | 0.132 / 0.671 | 0.079 / 0.580 | 太书面，不适合短剧 |
| 两行成对翻（取第二行） | cue6 仍错，cue36 合并前句 | cue6「だから私、去ったんです」、cue36 陈述句 | 30B 有效，需限定场景 |

**关键结论**

1. 7B 的生产 prompt 已经是最佳整体方案；上下文/术语表/风格指令在 7B 上全部显著变差（术语表还会把“都怪三哥”改成“都怪朵朵”），不要往生产 prompt 里加。
2. 30B-A3B 单独用不划算：风格更自然但人名漂移（ドゥドゥ/ドードー/ドゥオドゥオ、ヨンウ/ユウちゃん），且 38 条比 7B 慢 3–8 倍。
3. 30B 的价值在“两行成对翻”：把上一句和当前句一起给它、只取第二行，17.60「我才走的」能翻成「だから私、去ったんです」，96.12 变成陈述句；9f 的三条“就…”也翻得对。
4. 加载：模型架构是 `hy_v3`，turboquant 构建不认识；`web-llama/llama.cpp-vkopt/build-vk-cuda` 可以。`--cpu-moe` 只占 **2.2GB** 显存、38 条 19.2s；`--n-cpu-moe 10` 占 **15.4GB**、38 条 7.1s。混合方案用 `--cpu-moe`，可以和 7B 同时驻留（2.2+4.7GB），翻译阶段不跑擦除。
5. 确定性检查：疑问/陈述规则在 38 条上只命中 96.12 这一处，零误报；回译相似度太噪（“朵朵→咚咚”都判低），Hy-MT2 当裁判会把两处错句都判“一致”，都不能用于自动改写。

**落地计划**

- [ ] 批量翻译保持 7B 生产 prompt，不改全局上下文/术语表。
- [ ] 新增“承接句”二遍翻：仅对以 就/才/所以/但是/可是/不过/结果/然后/于是/因此 开头，或含“才…的”结构的 cue，用 30B `--cpu-moe` 走两行成对 prompt，取第二行；长度/重复前句/人名不符则回退 7B 译文，并记 `translation_repairs`。
- [ ] `translation_flags.json` 只做确定性检查：疑问句无疑问标记、人名/术语不符、长度异常、空译；回译只做可选人工线索，不自动判定。
- [ ] 按需加载：batch 在 prepare 全部结束后启动 7B + 30B 修复服务，translate 完成立即卸载；webapp 用同一个管理器，禁止与擦除阶段重叠。配置增加模型路径、`--cpu-moe`、启动超时和端口。
