# OCR 提速：det 不该放大（2026-11-04）

一句话：**rapidocr 默认把字幕带的短边放大到 736px**，字幕带只有 192px 高时等于放大
3.8 倍再检测。改成「长边封顶 960」后单次识别 211ms → 28ms，`extract` 2.9x、
残留复查 2.8x，且 cue 集合与残留结果完全一致。

## 1. 根因

`pipeline.get_ocr()` 之前裸调 `RapidOCR(...)`，用的是默认检测参数：

```text
det_limit_type = "min"      # 把「短边」缩放到 det_limit_side_len
det_limit_side_len = 736
```

字幕带的实际形状是 **192×1080**（1080p 视频、0.68–0.78 的细长带状区域）。
按 min/736 会被放大成 **4151×736** 再喂检测网络——像素量翻了 14 倍，
而字幕字高只有 63px，放大对识别精度没有任何帮助。

实测（同一帧，192×1080）：

| det 参数 | 单帧耗时 |
|---|---:|
| min / 736（默认） | 211 ms |
| max / 960（长边封顶） | **28 ms** |
| max / 736 | 28 ms |
| max / 1280（不缩放） | 30 ms |
| max / 1600 | 30 ms |

因为 1080 宽的图在 max/1280 下不缩放，可见差别全部来自「放大」这一步。

## 2. 改动

1. `pipeline.set_ocr_opts(det_limit_side_len=..., det_limit_type=...)`：参数变了会重建
   OCR 会话（否则进程里已经建好的会话改不动——这个坑第一次改完没生效，白跑一轮）。
2. `convert.prepare` 在建会话**之前**落地参数（版面探测自己就会建会话）。
3. `config.yaml:ocr` 新增 `det_limit_side_len: 960` / `det_limit_type: max`，
   另留 `VE_OCR_DET_LEN` / `VE_OCR_DET_TYPE` 环境变量做 A/B。
4. `ocr_boxes(..., use_cls=False)`：字幕不会竖排，方向分类这一层直接省掉。

顺带把顺手试的两个方向排除掉（都写进配置但默认关）：

- `ocr.max_w`（识别前再把字幕带缩到 720）：det 已经封顶后**没有收益**，默认 0；
- `ocr.reuse_static`（字幕带像素几乎不变就复用上一帧结果）：实测只省 4%，
  因为字幕带里还压着人脸和背景，逐帧都在动，判据不成立，默认关。

## 3. 效果（ep04，89.8s，49 镜头）

| 环节 | 改前 | 改后 | 倍数 |
|---|---:|---:|---:|
| `extract`（OCR 建轨） | 91.0s | **30.4s** | 2.99x |
| `residual_scan`（残留复查） | 65.1s | **23.5s** | 2.77x |

`extract` 内部拆解（改前）：OCR 71.6s / 解码 16.8s / 版面 10.0s / 拆条 5.8s。

端到端（4 支片，K=4，pipe=2，压制 3 并发）：

| 阶段 | 改前 | 只上流水 | 流水 + OCR |
|---|---:|---:|---:|
| 墙钟 | 609.6s | 463.6s | **354.4s** |
| 支/日(100%) | 566.9 | 745.5 | **975.2** |
| 源小时/日 | 15.36 | 20.20 | **26.43** |
| 实时倍率 | 1.56x | 1.19x | **0.91x** |

| 显存峰值 | 12493MB | 14287MB | 11979MB |

## 4. 验收

- **cue 集合**：ep04 走完整 `prepare` 后，两套 det 参数产出的 `state.json` 里
  38 条 cue（文本 + 起止）**逐条完全一致**。
- **残留**：同一份成片跑 `residual_scan`，两套参数都是 5 处、位置完全相同
  （32.69 / 33.67 / 59.24 / 80.36 / 80.80）。
- **原始抽帧层面**（`clean_cues` 之前）确实有少量差异：5 处文本变化里 2 处更好
  （`测试一 下`→`测试一下` 的空格断字消失；一条被 det 截断的长句恢复完整），
  2 处更差（`装穷`→`装究`、latin 噪声框位置不同），另有一处 cue 合并边界变化。
  这些差异在下游 `merge_cues/drop_junk/clean_cues` 之后被抹平。
  **结论：这批片子上是免费提速，但抽帧层面不是逐位等价，换片（低对比/极小字号/
  竖排）要重新对一次。**

## 5. 顺手补的健壮性

`convert.erase` 的单个镜头失败时（并发高时 NVENC 抢不到会话/显存，实测 4 路并发
跑 ep07 时镜头 74 就这样挂过一次，整支片白跑），现在会**改用 x264 中间层重试一次**
再决定是否失败，日志里能看到 `镜头 74 失败（RuntimeError），改用 x264 中间层重试`。

## 6. 还没做的

- 抽帧层面的 5 处文本差异，想让它们也消失就需要「det 快速初筛 + 可疑行高分辨率复核」，
  目前收益不值得加复杂度。
- 还可以把 `detect_layout`（10s）和 `detect_shots`（5.8s）合并到一次解码里，
  加起来还有 ~15s 的空间。
