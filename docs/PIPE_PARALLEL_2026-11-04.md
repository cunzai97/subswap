# 擦除段镜头级流水 + 压制线程池（2026-11-04）

结论：**擦除段不是算力不够，是片内串行**。把镜头流水化 + 压制进线程池后，
同一批片子端到端 1.50x（566.9 → 851.4 支/日），成片帧数与画质不变。

## 1. 数据先说话

20 集长跑（2026-11-04）已经暴露了症状：擦除段占 prepare 的 57%，
但**整段 GPU 平均只有 34.9%（p50 25%，≥80% 仅 15%）**。

原因在 v6 引擎的结构：`erase_shot_ref` 对每个镜头做两遍串行扫——

1. 第一遍（纯 CPU）：逐帧解码 → 白字门控 → 写 raw 帧和掩码到临时文件；
2. 第二遍（GPU + CPU）：再解码一遍 → 光流/光度校验/参考帧回填/时域稳定 →
   只有“没有干净参考”的帧才进 LaMa。

两遍之间、以及第二遍的每帧之间都是严格串行：GPU 跑一批 8 帧的同时，
CPU 侧的掩码、光流、合成、编码全在旁边等。镜头之间也一样。

## 2. 改动

### 2.1 `webapp/convert.py:erase()` 支持 N 路镜头并行

- 新增 `pipe` 参数（`ERASE_PIPE` 环境变量 / `worker.erase_pipe` 配置 / 参数，三处都能给）；
- 每个镜头一个任务进线程池，各写自己的 `segments/shot_XXXX.h264`，拼接顺序按镜头号，
  谁先完成都不影响成片；
- 模型调用用 `_SerialModel` 包一层锁：GPU 一次只能跑一个 batch（16GB 卡也放不下两份
  前向激活），能并行的是 CPU 那部分——解码、字形掩码、光流、光度校验、合成、编码。
- 单跑默认 4 路（`os.cpu_count()>=12`），批量由 `batch_pipeline` 按并发数下调。

### 2.2 `scripts/batch_pipeline.py` 压制进线程池

原来尾巴是「翻译 1.5min 串行 → 压制 5.0min 串行」。压制只吃 NVENC/CPU，
和翻译（占 GPU 显存）、以及别的支的压制都不冲突，所以翻译完一支就丢进线程池，
默认 3 并发（`--burn-jobs`）。日志里能看到 `[ep04] translate START` 之后 5 秒
`[ep04] burn START`，和后面几支的翻译重叠。

### 2.3 并发与中间层编码联动

NVENC 中间层每个实例占 **372MB 显存**（实测 8 个 writer ≈ 3GB）。并发上到 5 路时
这笔钱会直接撑爆 16GB，所以 `--writer auto` 在 `--jobs>=5` 时自动改 **x264**
（crf14，不吃显存，吃 CPU 约 80fps/路），并同步把 `ERASE_X264_THREADS`
按流水路数摊（`max(2, 12//pipe)`），避免 2 路 writer 抢空 12 个线程。

## 3. 实测

同一批片（ep04/07/11/13，390s 源），V100 独占，cwd=`batch_pipeline`：

| 配置 | 4 支墙钟 | 支/日(100%) | 源小时/日 | GPU 均值 | 显存峰值 |
|---|---:|---:|---:|---:|---:|
| 老行为：pipe=1 + 压制串行（NVENC） | 609.6s（10.2min） | 566.9 | 15.36 | 31.4% | 12493MB |
| 新：pipe=2 + 压制 3 并发（NVENC） | 463.6s（7.7min） | 745.5 | 20.20 | 45.3% | 14287MB |
| 新：5 路 + x264 + 压制 3 并发 | 507.4s / 5 支 | 851.4 | 24.31 | 49.5% | 14301MB |

第三行是 5 支片（513.9s 源），所以看 `支/日` 和 `源小时/日` 更有意义：
**851.4 支/日、24.31 源小时/日，1.50x**（对第一行）。

单跑一支 89.8s 片（只跑擦除，49 个镜头）：

| pipe | 擦除墙钟 | 加速 | 显存峰值 |
|---|---:|---:|---:|
| 1 | 281.3s | 1.00x | 9774MB |
| 2 | 158.6s | 1.77x | 5266MB |
| 4 | 94.1s | 2.99x | 6015MB |

（管道里 4 路跑得比 1 路还省显存，是因为单路时 torch 缓存分配器会吃掉整块空闲显存。）

### 3.1 画质验收

- 帧数：pipe=1/2/4 三份成片全部 2245 帧，与源一致；5 支交付片 2245/3092/2912/1595/3003
  全部 `时长×25` 精确值，未掉帧。
- 画质：pipe=1 vs pipe=2 **PSNR 96.2dB**，pipe=1 vs pipe=4 **PSNR 96.5dB**
  （差异全部来自 NVENC 非确定性重编码；路由、掩码、参考帧选择都没变，因为每个镜头
  的计算是自洽的）。
- 交付级：5/5 成片通过 `verify_burn`（帧数/时长/音轨/ASS/字体/渲染）。

### 3.2 并发天花板（踩过的坑）

| 配置 | 结果 |
|---|---|
| K=4 + pipe=2 + NVENC | ✓ 14287MB，稳 |
| K=4 + pipe=4 + NVENC | ⚠ 16051MB/16384MB，只剩 333MB，别上 |
| K=5 + pipe=2 + NVENC | ✗ CUDA OOM（5×2.6GB + 10×372MB writer） |
| K=6 + pipe=2 + batch4 + NVENC | ✗ CUDA OOM |
| K=5 + pipe=2 + x264 | ✓ 14301MB，稳 → **推荐** |
| K=6 + pipe=2 + x264 | ✗ cuFFT 内崩（显存压到极限） |

## 4. 用法

```bash
# 批量：5 路 + 自动（pipe=2、x264、压制 3 并发）
python3 scripts/batch_pipeline.py --src-dir ~/视频 --jobs 5 --target ja

# 回到老行为（A/B 对照或排障）
python3 scripts/batch_pipeline.py --jobs 4 --erase-pipe -1 --burn-jobs 1 --writer nvenc

# 单跑（网页/CLI）：默认 4 路，想关掉
ERASE_PIPE=1 python3 scripts/pipeline.py in.mp4 --out outputs/x --target ja
# 或者 config.yaml:
worker:
  erase_pipe: 0    # 0=自动，1=串行
  burn_jobs: 3
```

## 5. 风险与注意

1. **线程安全**：`_SerialModel` 只锁 `model(...)`；`pipeline` 模块里的 OCR 单例不参与擦除；
   每个镜头写自己的分段文件，拼接在全部完成后按镜头号进行。
2. **显存**：路径依赖 tmp 目录。擦除第一遍会把整镜头的 raw 帧+掩码写到
   `tempfile()`（本机落在 `/tmp`，root 分区只剩 ~14GB），pipe 越大并发临时文件越多，
   建议 `/tmp` 至少留 2GB/路。
3. **磁盘/编码**：`ERASE_WRITER=x264` 时中间层质量更好但吃 CPU；流水开大时务必
   让它按路数分线程（已自动处理）。
4. **回滚**：`ERASE_PIPE=1` + `--burn-jobs 1` + `--writer nvenc` 就是老行为，
   三个开关相互独立，可以单独回。
5. **还没吃到满**：pipe=4 单跑时 GPU 也只有 36.8% 均值，说明瓶颈还在 CPU
   （两遍解码 + 光流）。下一步该动 OCR 两遍扫描（P2）和片内解码复用，
   而不是继续加并发。
